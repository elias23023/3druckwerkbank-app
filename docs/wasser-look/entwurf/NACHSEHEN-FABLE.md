Written by Claude Opus 5.5, which finished this step after a first attempt (12:53 to 15:00, also Opus 5.5) was cut off by a usage limit. Most of the tool code of this step comes from that first attempt; what I added or checked is said per point.

1. **`sollist.mjs` does not compare the water inside a drop (`ok*`).** `scripts/wasser/sollist.mjs`, function `pair()`, variable `onlyWater`. A screen whose pixels differ only inside the drop canvases counts as equal when the drops themselves (number, place, size, label) are the same. Why it was done: two loads of ONE build differ there - I ran the same build on both sides with `--tropfen` (`--nur bogen-bereich,bogen-versionen,hinweis`, desktop, both formats and tones): 10 of 16 screens differed, all of it inside drops. Why it is a risk: a change that alters ONLY the water in drops (a shader change in `wasser.js`, `--wa-drop-veil`, the drop tokens) passes `sollist.mjs` as `ok*` without a word. How to check: for any change to the drops run `sollist.mjs --tropfen` and judge the listed screens by eye, or make the drop water deterministic (the "seed" running number in `wasser.js`) so the exception can go.
2. **Four checks failed under load and passed alone; which check failed was not recorded.** In the first attempt two queues of commands ran side by side; `pruefen.mjs --regler`, `pruefen.mjs --app --look screenshots/wasser/probe`, `desktop.mjs pruefen --look screenshots/wasser/probe` and `desktop.mjs pruefen --format 1920 --ton klar` each ended with "1 check failed". Its log kept only the last two lines, so I do not know which check. Run alone (by me, one at a time): 60/60, 24/24, 24/24 and all eleven governor checks. Suspects: the timing windows of check 11 (governor), the dock bead (3.3 px once under load, guide pitfall 65 area), check 9 "scrolling the sheet pulls its light". How to check: run `desktop.mjs pruefen` and `pruefen.mjs --app --regler` while a second heavy job runs, and keep the FULL output.
3. **The stricter guard against a wrong CSS order is new and only tested on today's stylesheets.** `scripts/wasser/lib.mjs`, `strangers()` and `lookStart()` (my change). Every top-level rule after the first `[data-wasser` must name `[data-wasser` or `data-wa-ton`; `@keyframes` / `@property` are skipped, `@media` / `@supports` / `@layer` / `@container` are looked into. Tested: the built CSS of this branch and of `feinschliff-basis` (0 strangers), the three template files joined (0), and two made-up cases (an app rule after the look, plain and inside `@media`: both caught). Not tested: `@scope`, `@font-face` or `@import` inside the look, CSS nesting at the top level of a built file. A false alarm stops every tool that replaces or removes the look. How to check after a template change: `node -e "import('./scripts/wasser/lib.mjs').then(m=>console.log(m.lookStart(require('fs').readFileSync('dist/assets/'+require('fs').readdirSync('dist/assets').find(n=>/^index-.*\.css$/.test(n)),'utf8'))))"` must print a number, not throw.
4. **The tone is set by writing the app's stored state.** `lib.mjs`, `setTheme()` (first attempt). It reads `3druckwerkbank:bereich`, writes `state.settings.theme` into `3druckwerkbank:v1` or `...:echt:v1`, replaces `Storage.prototype.setItem` with a no-op until the reload and reloads. It depends on the store's persist format; if that changes, the tools throw "tone: ..." (loud, which is right). Not covered: `ton: 'auto'` is never verified (the hour decides), and the frozen `setItem` would swallow a save if the reload did not happen. How to check: the four-way proof script (point 9) after any change to `src/store.ts` persistence.
5. **Options that belong to another part of a tool are still ignored in some tools.** Unknown options end every tool (first attempt). How to check: read each tool's `args(...)` against what each branch reads.
